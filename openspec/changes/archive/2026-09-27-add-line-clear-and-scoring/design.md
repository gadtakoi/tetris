# Design

## Context

Архитектуру задало изменение `add-core-game-logic`: пакет `tetris/` без pygame, `Board` хранит сетку `list[list[PieceType | None]]` размером 10×22, а `Game._lock()` делает `board.place(...)` → `_spawn(next_type)`. Метод `_lock()` с самого начала задуман как место, куда встраивается очистка линий. Мотивация описана в proposal.md (раздел Why), требования — в `specs/line-clear`, `specs/scoring` и дельте `specs/piece-control`.

## Goals / Non-Goals

**Goals:**
- Встроить очистку и очки в существующую последовательность фиксации, не меняя сигнатур команд и `StepResult`.
- Сделать правила очков и уровня чистыми функциями, которые проверяются без поля и без фигур.
- Оставить удобную точку расширения для будущей гравитации: уровень доступен как атрибут `Game`.

**Non-Goals:**
- События и колбэки о фиксации и очистке (observer). Интерфейс будет читать состояние после каждой команды.
- Возврат номеров удалённых строк для анимации. Появится вместе с line clear delay, если понадобится.

## Decisions

### `Board.clear_full_rows() -> int`
Метод находит заполненные строки, собирает список оставшихся строк в прежнем порядке, дополняет его сверху пустыми строками до 22 и заменяет `_grid`. Возвращает число удалённых строк. Реализация «отфильтровать и дополнить» выдаёт правильный сдвиг для несмежных строк по построению, без цикла со сдвигами по одной строке.

Альтернатива — держать очистку в `Game`. Тогда `Game` лезет во внутреннюю сетку поля, а сценарии спецификации `line-clear` пришлось бы тестировать через целую партию. На уровне `Board` их можно проверить напрямую, заполнив поле через `place`.

### Модуль `tetris/scoring.py` с чистыми функциями
```python
LINE_CLEAR_POINTS = {1: 40, 2: 100, 3: 300, 4: 1200}
LINES_PER_LEVEL = 10

def points_for(lines_cleared: int, level: int) -> int   # 0 при lines_cleared == 0
def level_for(total_lines: int) -> int                  # total_lines // 10
```
Таблица и формулы отделены от `Game`, поэтому сценарии `scoring` с заданным уровнем (например, «три линии на уровне 9») проверяются одной строкой, без того чтобы доигрывать до уровня 9. При `lines_cleared` вне 0–4 функция бросает `ValueError`: такого не может случиться, так как фигура занимает не больше 4 строк, и лучше упасть громко.

Альтернатива — класс `ScoreKeeper` с состоянием. Он избыточен: состояние — это три целых числа, которые естественно хранить прямо в `Game`.

### Состояние в `Game`
Новые публичные атрибуты: `score`, `lines`, `level`, `last_cleared` (все `int`). Они инициализируются в `new_game()`. `_lock()` становится таким:

```
board.place(cells, type)
cleared = board.clear_full_rows()
last_cleared = cleared
score += points_for(cleared, level)   # level ещё старый
lines += cleared
level = level_for(lines)
_spawn(next_type)                      # block out на очищенном поле
```
Уровень пересчитывается из `lines`, а не увеличивается на 1. Так он всегда согласован с числом линий, даже при переходе через два порога сразу (это станет возможным, если позже появится стартовый уровень).

`last_cleared` — атрибут, а не новое значение `StepResult`. Так не ломается API, от которого зависят существующие тесты и будущая гравитация.

### Тестовые позиции через `board.place`
В тестах `Game` поле готовят вызовом `game.board.place(...)` до управления фигурой, а активную фигуру задают через `ScriptedRng` и команды. Так уже делаются существующие тесты фиксации, новых тестовых хуков в `Game` не нужно.

## Risks / Trade-offs

- [Метод `clear_full_rows()` публично меняет поле, и слой отрисовки теоретически может его вызвать] → соглашение архитектуры: интерфейс только читает состояние. Отдельную защиту не добавляем.
- [`last_cleared` перезаписывается при каждой фиксации, и интерфейс, который опрашивает состояние реже фиксаций, может пропустить событие] → фиксация происходит только внутри `step_down()`, после которого интерфейс и так читает состояние. Если понадобится надёжнее, позже добавим очередь событий.
- [Уровень растёт без ограничения, а таблица скоростей следующего изменения конечна] → то изменение само ограничит скорость на последнем значении, `level` при этом не меняется.

## Migration Plan

Не требуется: добавляются новые атрибуты и методы, существующее API не меняется, сохранённого состояния нет.
