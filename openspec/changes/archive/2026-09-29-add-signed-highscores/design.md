# Design

## Context

Мотивация — в proposal.md, требования — в дельте `specs/high-scores/spec.md`.

**Сейчас:**
- `tetris/highscores.py` знает всё о JSON-виде таблицы. `HighScores.to_json()` выдаёт `{"version": 1, "entries": [...]}`, а `HighScores.from_json()` разбирает его, пропускает некорректные записи и возвращает пустую таблицу при другой версии. Константа `FORMAT_VERSION = 1` лежит там же.
- `tetris_ui/storage.py` читает и атомарно пишет файл (`load(path)`, `save(scores, path)`, `_write_atomic()`). Он же выдаёт пути от `data_dir()`.
- `app.create_controller()` загружает таблицу и передаёт в контроллер `on_save=lambda scores: storage.save(scores, scores_path)`.
- `tetris/` — чистая логика без файлового ввода-вывода. Это проверяют тесты архитектуры и соглашения проекта.

**Активное изменение `rename-data-folder`** меняет (MODIFIED) требование «Хранение таблицы», в тексте которого записан формат `version: 1`. По соглашению проекта одно требование меняет не больше одного активного изменения.

## Goals / Non-Goals

**Goals:**
- Правила таблицы (`tetris/highscores.py`) не знают ни о ключе, ни об ID, ни о файле.
- Подпись проверяется по записям в том виде, в каком они лежат в файле, до того как некорректные записи отброшены. Иначе правка, превращающая запись в некорректную, осталась бы незамеченной.
- Весь новый код, кроме одной строки в `app.py`, тестируется без pygame.

**Non-Goals:**
- Сокрытие ключа (обфускация, шифрование, вынос в C-расширение).
- Общий механизм подписи для других файлов.

## Decisions

### Логика отдаёт записи, а обёрткой файла занимается `storage`
В `tetris/highscores.py`:
- `HighScores.to_records() -> list[dict]` — записи как список словарей `name/score/lines/level`, лучшие первыми;
- `HighScores.from_records(raw: object) -> HighScores` — разбор списка: не список даёт пустую таблицу, некорректные записи пропускаются, затем устойчивая сортировка и обрезка до 10, как сейчас в `from_json()`.

`to_json()`, `from_json()` и `FORMAT_VERSION` из логики уходят. Номер формата, подпись и JSON-текст файла теперь в `storage`.

Отвергнуто: **подписывать в `HighScores.to_json()`.** Тогда в логике оказались бы секретный ключ и ID установки, то есть сведения о конкретной установке и сборке, а не правила игры.

### Модуль `tetris_ui/signing.py` без pygame
- `KEY: bytes` — 32 случайных байта, записанные в код один раз при реализации (`secrets.token_bytes(32).hex()`, результат вставлен литералом `bytes.fromhex("...")`).
- `signature(install_id: str, records: object) -> str` — `hmac.new(KEY, payload, hashlib.sha256).hexdigest()`, где `payload` — это `json.dumps({"version": 2, "install_id": install_id, "entries": records}, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")`.
- `is_valid(sig: object, install_id: str, records: object) -> bool` — `False`, если `sig` не строка; иначе `hmac.compare_digest(sig, signature(install_id, records))`.

Каноническая сериализация через `sort_keys` и фиксированные разделители не зависит от отступов и порядка ключей в файле. Число `100` и `100.0` сериализуются по-разному, но `100.0` и так некорректное значение очков.

`records` берутся из файла как есть, без разбора. Поэтому любая правка записи, даже превращающая её в некорректную, меняет подпись.

Отвергнуто: **SHA-256 от данных без ключа.** Любой пересчитает хэш сам. **Подпись Ed25519 с открытым ключом в игре.** Закрытый ключ всё равно нужен игре, чтобы подписывать, так что асимметрия ничего не даёт. К тому же понадобилась бы внешняя зависимость.

### ID установки — отдельный файл `install-id`
В `storage`:
- `INSTALL_ID_FILE = "install-id"` и `install_id_path()` рядом с остальными путями;
- `load_install_id(path) -> str`: читает файл, отрезает пробелы по краям и проверяет `re.fullmatch(r"[0-9a-f]{32}", text)`. Если ID подходит, возвращает его. Иначе (нет файла, ошибка чтения, неверное содержимое) создаёт `secrets.token_hex(16)`, пишет его через `_write_atomic()` с переводом строки в конце и возвращает, даже если запись не удалась.

Отвергнуто:
- **ID в `settings.json`.** Руководство игрока советует удалять `settings.json`, чтобы сбросить настройки. Это молча сбрасывало бы и рекорды. Кроме того, `Settings.from_json()` отбрасывает неизвестные поля.
- **ID из железа или реестра (`MachineGuid`, MAC).** Код зависит от ОС, раскрывает сведения о компьютере и ломается при замене оборудования. Перенести рекорды на новый компьютер тогда тоже нельзя.

### Формат и загрузка в `storage`
- `save(scores, path, install_id)`: `records = scores.to_records()`, текст файла — `json.dumps({"version": 2, "entries": records, "sig": signing.signature(install_id, records)}, ensure_ascii=False, indent=2)`, запись через `_write_atomic()`.
- `load(path, install_id)`:
  1. файла нет, он не читается или не декодируется → пустая таблица без предупреждения (как сейчас);
  2. некорректный JSON или не объект → пустая таблица без предупреждения (как сейчас);
  3. `version != 2` или `not signing.is_valid(data.get("sig"), install_id, data.get("entries"))` → `warn(f"high scores in {path} failed the integrity check; starting with an empty table")` и пустая таблица;
  4. иначе → `HighScores.from_records(data["entries"])`.
- `app.create_controller()` сначала получает `install_id = storage.load_install_id(storage.install_id_path())`, затем передаёт его в `storage.load()` и в `on_save`.

Файл при загрузке не трогается. Старую таблицу перезапишет первое сохранение, как и повреждённый файл сейчас.

### Требования: ADDED сейчас, формат в «Хранении таблицы» — при реализации
Пока `rename-data-folder` активно, дельта этого изменения только добавляет требования: «ID установки», «Подпись таблицы», «Неподтверждённая таблица». Первая задача реализации проверяет, что `rename-data-folder` уже архивирован. Затем в дельту добавляется MODIFIED «Хранение таблицы», где `{"version": 1, ...}` заменён ссылкой на требование «Подпись таблицы». Так после архивации в основной спецификации не останется двух противоречащих описаний формата.

## Risks / Trade-offs

- [Ключ извлекается из exe (PyInstaller распаковывается стандартными инструментами)] → Принято: в proposal это вне рамок. Защита рассчитана на правку в блокноте и копирование файла.
- [Таблица игрока после обновления пустая] → Решение игрока. `docs/user-guide.md` об этом говорит.
- [Если применить до архивирования `rename-data-folder`, «Хранение таблицы» будут менять два активных изменения, и при архивации одно затрёт правку другого] → Первая задача реализации проверяет порядок и останавливается, если `rename-data-folder` не архивирован.
- [Игрок удаляет `install-id` и теряет таблицу] → В руководстве файл описан как часть рекордов: копировать вместе с `highscores.json`, не удалять.
- [Смена ключа или канонического вида в будущем молча сбросит всем таблицы] → В docstring `signing.KEY` и `signature()` сказано, что их изменение требует нового номера формата и отдельного изменения OpenSpec. Тест с зафиксированной подписью (известный ID и записи → известный `sig`) ловит случайную правку.

## Migration Plan

Отдельного переноса нет. Файл `version: 1` при первом запуске считается неподтверждённым, таблица начинается пустой, и файл заменяется при первом рекорде. Откат на прежнюю сборку тоже даёт пустую таблицу: она не принимает `version: 2`.
