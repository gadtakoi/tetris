# Design

## Context

Проект пустой: есть только `.venv` на Python 3.14 и настроенный OpenSpec. Мотивация изложена в proposal.md (раздел Why), требования — в `specs/playfield`, `specs/tetrominoes` и `specs/piece-control`. Главное ограничение из контекста проекта: логика не импортирует pygame, детерминирована и проверяется pytest. Следующие изменения (гравитация и уровни, очистка линий и очки, интерфейс) будут встраиваться в эту логику, поэтому её API должен их выдержать без переделки.

## Goals / Non-Goals

**Goals:**
- Небольшой пакет `tetris/`, который можно полностью протестировать без окна и без времени.
- Точки расширения для следующих изменений: гравитация вызывает тот же «шаг вниз», очистка линий встраивается в последовательность фиксации.
- Детерминизм: одинаковые seed и последовательность команд всегда дают одинаковое состояние.

**Non-Goals:**
- Производительность: поле 10×22, оптимизации (битовые маски и т. п.) не нужны.
- Сериализация и сохранение состояния.
- Потокобезопасность: логика вызывается из одного игрового цикла.

## Decisions

### Структура модулей
```
tetris/
  __init__.py
  pieces.py      # PieceType, таблицы ориентаций, позиции появления
  board.py       # Board: сетка 10×22, is_free, get, place, visible_rows
  randomizer.py  # Randomizer: равновероятный выбор поверх random.Random
  game.py        # Game: активная/следующая фигура, команды, фиксация, конец игры
tests/
  test_pieces.py, test_board.py, test_randomizer.py, test_game.py
```
Разделение по сущностям из спецификаций, чтобы каждый модуль проверялся отдельно. Альтернатива — один модуль `game.py` — проще сейчас, но быстро разрастётся после добавления очков и уровней.

### Координаты — кортежи `(col, row)`
Во всём API клетки задаются как `(col, row)`, `row` растёт вниз, как в спецификации и как в экранных координатах pygame (x, y). Так слой отрисовки переводит клетку в пиксели без перестановки осей. Внутри таблиц форм используется (row, col) относительно рамки, как в спецификации, но наружу это не выходит.

### Таблицы ориентаций вычисляются один раз
В `pieces.py` вручную задаются только клетки ориентации 0 и размер рамки (как в таблице спецификации). Ориентации 1–3 вычисляются при импорте формулой `(r, c) → (c, N−1−r)` и хранятся как кортежи `frozenset`/`tuple`. Альтернатива — вписать все 28 вариантов руками — легко ошибиться, а формула прямо соответствует требованию и проверяется тестами. Для O формула не применяется: в рамке 4×4 она сдвигала бы квадрат, поэтому все четыре ориентации O — копии ориентации 0.

### Неизменяемая активная фигура: «попробовать и применить»
`ActivePiece` — `@dataclass(frozen=True)` с полями `type`, `rotation`, `col`, `row` (левый верхний угол рамки на поле; может быть отрицательным, например у вертикальной I у левой стены) и методом `cells()`. Каждая команда строит кандидата (`dataclasses.replace`), проверяет `board.is_free` для всех его клеток и только тогда заменяет активную фигуру. Отклонённый ход ничего не меняет по построению — это прямо реализует требование «позиция и ориентация не меняются».

### Результаты команд
- `move_left()`, `move_right()`, `rotate_cw()`, `rotate_ccw()` возвращают `bool` (выполнен ли ход).
- `step_down()` возвращает `StepResult` — перечисление `MOVED | LOCKED | REJECTED`. Одного `bool` мало: спецификация требует сообщать о фиксации, а интерфейсу и гравитации нужно отличать «опустилась» от «зафиксировалась». `REJECTED` возвращается только после конца игры.

### Последовательность фиксации — отдельный метод
`Game._lock()` делает: `board.place(cells, type)` → (здесь позже будет очистка линий и начисление очков) → `_spawn(next_type)` → выбор новой следующей фигуры. `_spawn` при занятой позиции появления ставит `is_over = True` и не заменяет активную фигуру. Так изменение с очисткой линий добавит один вызов в известное место.

### Случайность внедряется
`Game(seed: int | None = None, rng: random.Random | None = None)`. Внутри — `Randomizer(rng)`, который вызывает `rng.choice(list(PieceType))`. Тесты передают либо seed, либо заглушку `rng`, которая выдаёт заданную последовательность, — это нужно, чтобы детерминированно строить сценарии «следующей объявлена S». Альтернатива — глобальный `random` — делает тесты недетерминированными.

### Защита от импорта pygame
Отдельный тест импортирует все модули `tetris` в чистом процессе (`subprocess` с `python -c`) и проверяет, что `pygame` не попал в `sys.modules`. Это закрепляет архитектурное правило из контекста проекта автоматически, а не на ревью.

## Risks / Trade-offs

- [Без wall kicks вращение у стен и в узких местах часто отклоняется, игра ощущается «жёсткой»] → так задумано для классической версии; SRS вынесен за рамки и добавится отдельным изменением, заменив только проверку в `rotate_*`.
- [Без 7-bag возможны длинные серии без I-фигуры] → принято для классического поведения; генератор изолирован в `Randomizer`, замена на 7-bag не затронет `Game`.
- [Фиксация без задержки: фигура фиксируется на первом неудачном шаге вниз, нельзя «докрутить» её на дне] → соответствует классике; lock delay вынесен за рамки.
- [Python 3.14 новый — колёса pygame-ce под него могут отсутствовать] → на это изменение не влияет (нужен только pytest); проверить при изменении с интерфейсом, при необходимости создать `.venv` на 3.13.
