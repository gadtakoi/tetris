# Design

## Context

`Game` уже умеет всё, что нужно одному шагу гравитации: `step_down()` опускает фигуру или фиксирует её (фиксация включает очистку линий и очки), `_spawn()` выпускает следующую фигуру, а `level` пересчитывается после каждой фиксации. Не хватает часов. Контекст проекта требует, чтобы время передавалось в логику явно и логика не читала системные часы. Мотивация описана в proposal.md, требования — в `specs/gravity`.

## Goals / Non-Goals

**Goals:**
- Точная целочисленная арифметика времени, без накопления ошибок float и без округления интервала 716⅔ мс.
- Гравитация переиспользует ту же последовательность шага и фиксации, что и команда игрока, без копирования логики.

**Non-Goals:**
- Сообщать интерфейсу о событиях внутри `tick` (сколько шагов сделано, была ли фиксация). Интерфейс читает состояние после вызова, как и после команд.
- Защита от огромных `dt` (например, после сворачивания окна). Если интерфейсу понадобится, он сам ограничит `dt` сверху.

## Decisions

### Модуль `tetris/gravity.py`
```python
FRAMES_PER_SECOND = 60
_FRAMES_BY_LEVEL = (48, 43, 38, 33, 28, 23, 18, 13, 8, 6)  # уровни 0–9
# диапазоны: 10–12 → 5, 13–15 → 4, 16–18 → 3, 19–28 → 2, 29+ → 1

def frames_per_row(level: int) -> int
```
Таблица хранится в кадрах, как в спецификации, а не в миллисекундах. Так она проверяется построчно, и нет места для ошибок округления. Как и `scoring.py`, это чистые функции, которые тестируются без `Game`.

### Время в единицах 1/60 мс
`Game` хранит накопленное время `_gravity_time` в целых «единицах» по 1/60 мс:
- `tick(dt_ms)` прибавляет `dt_ms * 60`;
- интервал уровня в тех же единицах равен `frames_per_row(level) * 1000`: F/60 с = F·1000/60 мс = F·1000 единиц.

Все значения целые, поэтому сравнение и вычитание точные. Сценарий «716 мс — ещё нет, 717 мс — уже да» на уровне 1 выполняется без эпсилонов: 716·60 = 42 960 < 43 000 ≤ 43 020 = 717·60.

Альтернативы:
- `float` секунды: накапливают ошибку, и граничные сценарии становятся хрупкими.
- `fractions.Fraction`: точно, но медленнее и шумнее, а выигрыша по сравнению с целыми нет.

### `tick(dt_ms: int) -> None`
```
if dt_ms < 0: raise ValueError        # до любых изменений
if is_over: return
_gravity_time += dt_ms * 60
while not is_over and _gravity_time >= interval(level):
    _gravity_time -= interval(level)
    _advance()                        # шаг вниз или фиксация
```
Интервал перечитывается на каждой итерации, поэтому уровень, повышенный фиксацией, сразу действует. Фиксация вызывает `_spawn()`, который обнуляет `_gravity_time`, так что цикл после фиксации завершается сам и остаток отбрасывается, как требует спецификация.

### Разделение шага на внутренний и командный
Текущее тело `step_down()` переносится во внутренний `_advance() -> StepResult` (попробовать опустить, иначе `_lock()`). Публичный `step_down()` вызывает `_advance()` и при `MOVED` обнуляет `_gravity_time`. Гравитация зовёт `_advance()` напрямую. Так сброс «по команде игрока» не срабатывает от шагов гравитации, а правила шага и фиксации остаются в одном месте.

Альтернатива — флаг `step_down(by_player=True)`. Она загрязняет публичное API параметром, который интерфейсу никогда не нужен.

### Сброс в `_spawn()` и `new_game()`
`_spawn()` обнуляет `_gravity_time` при любом исходе, в том числе при block out. `new_game()` обнуляет его явно: `_spawn()` там не вызывается, первая фигура создаётся напрямую.

## Risks / Trade-offs

- [На уровнях 29+ интервал 16⅔ мс близок к длительности кадра, и при неравномерном FPS фигура может проскакивать несколько строк за кадр] → так и задумано: один вызов с большим `dt` честно выполняет несколько шагов, поэтому скорость не зависит от FPS.
- [Сброс при мягком падении отличается от поведения NES, где счётчик гравитации не сбрасывается] → осознанное упрощение, оно исключает двойной шаг. Решение записано в спецификации и при необходимости меняется в одном месте, в `step_down()`.
- [`_gravity_time` — внутреннее состояние, и тесты не должны на него опираться] → тесты проверяют только наблюдаемое положение фигуры после серий `tick`, как в сценариях спецификации.

## Migration Plan

Не требуется: API только расширяется, существующее поведение `step_down()` для игрока не меняется.
